# 設計ノート: 設計文書のグラフと増分の天井（判断の記録 ADR-13 の下調べ）

- 位置: 持ち主の問い（2026-09-22 01:1x・対話面 R-8）「増分の天井（変わった file だけ見る）では他の仕様や憲法との整合が見られない。憲法は小さいので毎回見てよいが、仕様はグラフ化が要るのでは。folio は各要素にリンク（id 参照）を付けさせているので、リンクをノードの辺として使い、変更で影響を受けうる所を機械的に導出できないか。あるいはリンクとノードの対応をしっかり作り込む方向で設計を根本から考え直すか。AI にとって全体像が常に安く速く得られることが設計文書として最重要」。
- 出所: 判断の記録 ADR-8 の注が持つ門の撤退条件「設計文書を触る便が 1 週間に 5 本を超え、周の費用が便の費用の合計を超えたら、文書ごとの印の設計ノートを起こす」。この条件は §1.6 の実測で発動している。設計ノート docs/design/ceiling-gate.md の §4 案 B（文書ごとの印）が、そのとき起こす設計ノートの素描だった。本ノートはその後継で、単位を **文書より細かい節点** に置く。
- 状態: 起草（未裁定）。🔴 の問いは §10 の 5 つ。判断の記録 ADR-13 は本ノートの §2〜§7 を決定に写した草稿（status: proposed）。
- 読む人: 持ち主（🔴 の判断）・orchestrator 席（便の契約を書く）・天井の観点の AI（増分の読む範囲を受け取る側）。
- 憲法との関係: 本ノートは規則を持たない（N-2）。閾値・値域・閉じた一覧の正本は要件書と規則の表と実装の型付きの定数で、ここには写さない（P-5.1・P-5.5）。観点は 4 つのまま増やさない（N-5）。

**先に結論**: グラフは作れる（辺は 641 本が既に在る）。ただし **起草の途中で節が 1 つ覆った**。当初は「近傍は 1 段で足りる」と書いたが、過去 23 周・整合の所見 142 件を数えたところ 1 段では 74% しか捕まえられず、「止める」の 12 件のうち 1 件を取りこぼした（§1.7）。**採るのは半径 2 である。** 費用の節約は当初見積の「1 周あたり 5%」ではなく **1 周あたり 26%（いまの 1/4）** で、それとは別に **40 回の変更のうち 13 回（33%）は周そのものが要らなくなる**。

## 2. 節点と辺の型（本ノートが使う新しい語）

語彙 `design-intent/vocabulary.yaml` に 節点・辺・影響集合 は無い（54 語を実測）。発効するなら語彙に足す。ここでは定義だけ置く。

### 2.1 節点

**節点** = 設計文書の中で id を持ち、1 つのまとまりとして読める単位。次の 5 欄を持つ。

| 欄 | 中身 |
| --- | --- |
| id | その節点を指す字（`P-1.2`・`FR20`・`R-7`・`ADR-8`・`AC18`・`GOAL1`・設計ノートの `<文書 id>§<n>`・語彙の語の id・天井の観点の id・要件書の節の名） |
| 種類 | 閉じた一覧（条・規範文・規則行・目的・要件・非機能要件・受入基準・制約・判断の記録・設計ノートの節・語・欄の語・天井の観点・天井の節・入口の節・相談の問い・相談の節・要件書の節・憲法の節）。一覧の正本は実装の型付きの定数（P-5.1）で、生成区間へ導出する（FR19 と同じ形） |
| 所属 file | repo の根からの相対 path |
| 欄の要約値 | その節点の本文（欄を並び順で正規化した字）の sha256。§1.6 の「変わった」はこの値の比較で決まる |
| 題 | 1 行（`title`・無ければ `what`・`term`・`text` の頭） |

節点の粒は **id を持つ行と、id を持たないが所見の場所になる節** に取る。file より細かく、欄より粗い。理由は 3 つ。

1. 天井の所見は既に「場所」を `{doc, at}` で書いている（所見の欄の決まり・ADR-8 決定 (3)）。§1.7 の実測で、その場所の 62% は id で、残り 38% は節の名（語彙の語・天井の観点・要件書の scope）である。**節点の一覧は、所見が置ける場所の一覧と一致していなければならない。** 一致しなければ、その場所の所見は影響集合で扱えない。
2. 欄まで細かくすると、辺の端が「どの欄が何の欄に依存するか」になり、いま在る欄（`basis` は条の id を持つだけで、条のどの欄かは言わない）からは導けない。持っていない情報を持っているふりをしない（P-4）。
3. file の粒では §1.6 のとおり中央値で 22% の文書が丸ごと古くなる。

節点にしないもの: 生成区間（`schema` 節）・`meta`（承認の来歴・版の来歴）・凍結 anchor・生成物（`preview/`）。**生成区間の変更は床（`folio schema --check`）が別に数えており、天井の領分ではない**（P-3.1）。§1.6 の 13 回の「節点が変わらない commit」はこの扱いから出る。§1.7 で「meta / 生成区間」に置かれた所見 7 件は、いずれも重さが 止める ではなく、その 7 件が指摘したのは注の字面である（注は節点の本文に含む＝節点にしないのは `meta` の節であって、行の `note` 欄ではない）。

### 2.2 辺

**辺** = 節点から節点へ引かれた向きのある結び。型は §1.2 の欄から取り、**閉じた一覧**（P-2.4 と同じ扱い）にする。

| 型 | 向き | 出所の欄 | 伝播に使うか |
| --- | --- | --- | --- |
| basis | 要件・判断 → 条・規則行・要件 | `basis` | 使う |
| verifies | 受入 → 要件 | `verifies`・`verify.ac` | 使う |
| refs | 要件・設計ノートの行 → id | `rules`・`ref`・`req` | 使う |
| amends | 判断 → 条 | `amends.target`・`amended_by` | 使う |
| relations | 条 → 条・要件・規則行・節 | `relations.*` | 使う |
| goals | 要件 → 目的 | `goals` | 使う |
| article | 規則行 → 条 | `article` | 使う |
| reads | 観点 → 文書の欄 | `viewpoints.reads` | 観点の読む範囲を決めるのに使う（節点間の辺ではない） |
| figures | 要件・判断 → 図 | `figures` | 使わない（図は別の正本） |
| mention | 任意の節点 → id | 散文の中の id（§1.3） | **使わない** |

**散文の言及（mention）を伝播に使わない理由。**

1. 数が多すぎる（1,709・型付きの 2.7 倍）。承認の来歴と決定の本文に集中しており、そこに現れる id の大半は「過去にこの版でこの条を直した」という **履歴** であって、いまの依存ではない。履歴を辺にすると、古い判断の記録 1 本を直しただけで影響集合が全体に広がる。
2. 向きが無い。`meta.status_note` の中の `FR19` は、その文書が FR19 に依存しているのか、FR19 を説明しているのか、区別できない。
3. 憲法 N-2 の向きに反する。**散文にしか無い依存が本当に依存なら、型付きの欄に書き写すべきであって、走査で救い上げるべきではない。**
4. **要らない。** §1.7 の実測で、型付きの辺だけで過去 23 周の 整合 の所見を 2 段以内に 100% 捕まえられた。mention を足す理由が無い。

mention は **読みの手掛かり** としてだけ出す。影響集合を出すとき、型付きの辺で届かない節点のうち、変わった節点の id を散文に含む節点を「参考」の列に別立てで並べる。AI はそれを読んでもよいが、床はそれを影響集合に数えない。所見の重さ（止める／直す／参考）の区別と同じ形にする。

### 2.3 グラフの正本はどこか

**グラフの正本は設計文書そのもの**（正本 YAML の欄）であり、索引は導出物である（P-6.3）。索引の file を人が書く面は作らない（P-6.4）。索引を持たない状態で影響集合を問われたら「まだ分からない」を返す（P-4.2）。

## 3. 影響集合（何を読み直すか）

### 3.1 定義

**影響集合** = ある変更について、天井の観点が読み直す必要のある節点の集合。観点ごとに違う。

入力は「変わった節点の集合 C」（2 つの版の欄の要約値の差）。

| 観点 | 読む範囲 |
| --- | --- |
| すべての観点（床） | **憲法（27 条・67 規範文）と、その付録（語彙 54 語・規則の表 28 行）と、天井の正本の観点の一覧** を毎周全部 |
| 忠実さ | 床 ＋ C |
| 読みやすさ | 床 ＋ C |
| 整合 | 床 ＋ C ＋（C から型付きの辺で **2 段** の近傍） |
| 実態 | 床 ＋ C ＋ C に結び付く実装の証拠（契約表の行の `req`・着地の印の要件 id・歯の名） |

**床に語彙と規則の表を入れる根拠は §1.7 の実測である。** 語彙の語（17 件）と天井の観点（12 件）に置かれた所見は、その節点が型付きの辺を 1 本も持たないため、伝播では永久に届かない。持ち主の指示は「憲法は小さいので毎回見てよい」だったが、語彙と規則の表は入口の棚で憲法の付録（`shelf.annexes` の `inside: constitution`）と定められており、**憲法の一部として毎周読むのは指示の字面の自然な読み** である。費用は §1.8 のとおり 886,260 byte の 30.8%。

**規則の表を床に入れるもう 1 つの根拠**: 4 観点すべてが `reads` に `rules: [thresholds, discipline]` を持っている（§1.2 の reads 73 本のうち 8 本）。いま既に毎周全部読んでいる。

### 3.2 なぜ 2 段で止めるか

- 1 段では足りない（§1.7・所見の 16%、止めるの 1/12 を取りこぼす）。
- 2 段で過去 23 周の 整合 の所見を 100% 捕まえた（同）。
- 3 段に広げても捕まる所見は増えず、費用だけが増える。次数の高い節点（P-5 が 35・ADR-8 が 32）を 2 つ通れば、辺を持つ節点 190 の大半に届く。

2 段で止める代わりに、**止めた先を隠さない**。影響集合の出力に「3 段目の節点の id の列」を別の欄で添え、観点の AI が必要と判断したら自分で読める形にする（正本は同じ repo にある）。

### 3.3 変わっていない節点の判定をどう扱うか

**持ち越し**。前の周で「その節点についての所見が 0 だった観点」は、前の判定を持ち越す。

持ち越しの条件を機械が数えられる形に置く。

1. 前の周の印が、節点ごとの要約値を持っている（§4）。
2. 今の節点の要約値が印の値と同じ。
3. その観点の影響集合（§3.1）に入る節点のうち、要約値が変わったものが 1 つも無い。

3 つが揃わなければ持ち越さない。1 つでも欠ければ「まだ分からない」で、その観点を回し直す（P-4.1・P-10.3）。**持ち越すのは「合格」だけで、「不合格」は持ち越さない**。不合格の観点は、その所見が指す節点が直っていれば回し直し、直っていなければ不合格のままにする。

「例外機構を足さない」（N-3.1）との関係: 持ち越しは判定を緩める旗ではない。同じ入力（同じ要約値）に同じ判定を返しているだけで、入力が 1 byte でも違えば持ち越さない。無効化の旗も「今回だけ」の口も持たない。

**ただし、これは天井の判定の持ち越しである**（§10 の問 3 で敵対的に問う）。天井は AI の判定であり、同じ入力でも同じ答えが返る保証は無い。床の合格を天井の合格として扱わないのと同じ用心が要る（P-3.3）。

## 4. 印と門を節点の単位に（要件書 FR20 の改訂の範囲）

### 4.1 いまの印

`design-intent/preview/ceiling-stamp.yaml`（生成物・便 72 で着地）は次を持つ。

```
round / at / verdict / sources: sha256 <全 sources の 1 つの要約値>
faces: sha256 <全 faces の 1 つの要約値> / viewpoints[] / refutes[] / reads[]
```

`sources` は **file の集合全体の 1 つの値**である。設計文書が 1 byte でも変われば古くなる（`ceiling-gate.md` §4 の「厳格」＝持ち主が裁定した段階 1）。これが 25 周の原因である。

### 4.2 節点の単位にした印

印に **節点ごとの要約値の表** を足す。

```
nodes:
  - {id: P-1, kind: 条, file: constitution.yaml, sha: <8 字>}
  - {id: P-1.1, kind: 規範文, file: constitution.yaml, sha: <8 字>}
  ...
viewpoints:
  - {id: fidelity, verdict: 合格, ..., covered: <この観点が判定を出した節点の id の列>}
```

節点は 285 なので、8 字の要約値と id と種類と file で 1 行 40〜60 byte、表全体で **約 16 KB**。いまの印（976 byte）に対して 17 倍だが、生成物 1 file で、版管理の履歴では行単位の差分として読める（P-6.2 のとおり手で直さない）。

### 4.3 門の 3 値（FR20 の判定をどう変えるか）

いまの `folio ceiling --gate` は、便の書き換える file の一覧（write-set）と印と今の正本から 3 値を返す。変えるのは「印が古いか」の測り方だけで、**3 値の意味も、「まだ分からない」が「不合格」より先に立つ順序も変えない**。

| 場合 | いま | 節点の単位 |
| --- | --- | --- |
| write-set に設計文書の正本が 1 つも無い | 通す（0） | 同じ |
| 印が 4 観点とも合格・正本の要約値が今と同じ | 通す（0） | 同じ（節点の要約値が全部一致） |
| 印に不合格の観点が在る | 止める（1） | **その観点が不合格を出した節点が、この便の write-set の中の file に在るときだけ止める。ほかの file の便は通す** |
| 印が無い・古い・「まだ分からない」の観点が在る | まだ分からない（2） | **古い = 印に無い節点が在る、または印の要約値と今の要約値が違う節点が在る。その節点が write-set の file に在るときだけ 2。ほかの file の便は通す** |

判定の対象を「repo 全体」から「この便が触る file の節点」へ狭める。狭めた結果を隠さないため、門の出力の 1 行に、通したときでも「印の古い節点 N 個（この便の外）」を必ず添える。

**この変更は門を緩める向きである。** 規則の表の閾値行の値を緩めるときは条 A-2.3 の検証を前置する（P-17.4）が、門の判定は要件書 FR20 の規範文であって規則の表の行ではない。ただし要件書の版上げは持ち主の承認を要する（P-12.1）ので、§10 の grill を経て承認要求に載せる。

### 4.4 止まった観点だけ回し直す

いまの 1 周は 4 観点を必ず全部回す。節点の単位にすると、直しの PR の後に回し直す観点は「その PR が触った節点を読む観点」だけになる。

**ただし観点の数はほとんど減らない。** 床（憲法 + 語彙 + 規則の表 + 天井の正本）を 4 観点とも毎周読むので、どの節点を触っても 4 観点とも引っかかる場合が多い。減るのは **1 観点あたりに読ませる量**（§1.8 の 26%）と、**周そのものが要らない回**（§1.6 の 33%）である。この区別を誤らないこと。

## 5. 実装の状態の注を導出物にする

### 5.1 いま何が起きているか

要件書の `note` 欄に、実装の状態が散文で書かれている。要件と非機能要件と受入基準と制約の `note` は合計 **14,577 byte**（要件書全体 100,349 byte の 14.5%）。

- FR11: 「この要件の口（導出物を組む・差分を数える）は未実装である（2026-09-20 時点）」
- FR13: 「この要件の口（commit の末尾の印から着地を読む）は未実装である（2026-09-20 時点・FR11 の後の便）」
- FR20: 「この要件の口は 2 つとも着地済みである（--stamp = 便 72・crates/folio/src/stamp.rs・台帳 f2-648.107・2026-09-21／--gate = 便 73・crates/folio/src/gate.rs・台帳 f2-648.108・2026-09-21）」
- NFR1: 「未達である（2026-09-20 時点・天井の 9 周目の止める所見 実態との整合 F-1・反証 支持）」

**日付が手で書かれている。** 天井の 実態 の観点は毎周この散文を読み、実装と食い違っていれば所見を立てる。要件書の版 v1.9〜v1.24 の 16 版のうち、注の実態合わせだけの版が複数ある（v1.16「約束と実態の総点検」・v1.21「FR20 / AC18 の注を今の状態に」・v1.22「FR19 / AC17 の対象に…便 76 / 77 の先行」）。**注を手で実態に合わせる作業が、天井の周を消費している。**

### 5.2 導出できる材料はもう在る

| 欲しい値 | 材料 | 実測 |
| --- | --- | --- |
| その要件を運んだ便 | 契約表の行の `req` | `docs/design/delivery-*.md` に 87 行・要件 id の参照 181 件（異なり 19・上位 FR5 が 40・FR4 が 30・NFR2 が 21） |
| その便が着地したか | 着地の commit の末尾の印（`Scribe2-Contract` と `Scribe2-Requirements`） | 全 310 commit のうち 34 commit |
| その要件の歯 | 受入基準の `red_test.fixture` と契約表の行の `verify` | 受入 18 件 |
| 台帳の起票 | bead の `acceptance_criteria` の design pointer（`design = docs/design/delivery-N.md#<行>`） | bead 125 件（closed 110・open 15）のうち 42 件が 40 本の契約の行を指す |

要件書 FR13 は「着地は印だけから読み、無ければ『まだ分からない』と出し『未着地』とは言わない」と既に定めている。FR11 は契約表からの導出物を、FR14 は機械が読む id の索引を定めている。**3 つとも未実装（台帳 f2-648.88）で、3 つともこの構想の部品である。** 床の穴（台帳 f2-648.114）「要件・判断の記録・受入基準の id の消失と改番を数える口が無い（P-7.1）」も、節点の索引が在れば数えられる。

### 5.3 どう変えるか

1. 要件ごとの実装の状態を **導出物** として出す。値は 3 値: 着地（印を持つ commit の sha を添える）・便が在るが印が無い（「まだ分からない」）・便が無い。
2. 要件書の `note` から「未実装である」「着地済みである」「（2026-09-20 時点）」の類の字を **落とす**。落とした先は導出物で、注は「状態は導出物が持つ」と 1 度だけ言う（制約 CON5 / CON6 が規則の表の行 D-1 / D-7 を参照するだけになったのと同じ形）。
3. 実態 の観点が読む相手を、注の散文から導出物へ替える。天井の正本の `viewpoints.reality.reads` はその向きに変える（欄の一覧は人が書く節なので承認を要する）。

注には実態以外の中身（判断の記録への出所・退けた案・母集団の断り）も多い。**落とすのは実装の状態を述べる文だけ**で、落とす前後の字は契約表の行に 1 本ずつ書く。

**この §5 は、人が読む面を劣化させる危険を持つ**（§10 の問 5）。

## 6. 全体像の安い出力

持ち主の言う「AI にとって全体像が常に安く速く得られること」への答え。

### 6.1 形

`folio graph --digest` が 2 つの表を標準出力へ書く。

```
# 節点（1 行 = id / 種類 / file / 要約値 8 字 / 題 36 字・タブ区切り）
A-1	条	constitution.yaml	e4784b48	消す・外へ出す・使う は確認してから
A-1.1	規範文	constitution.yaml	838bbbe4	既存の文書やデータを消す、外へ出す、外部の道具や鍵を使う（課金を含む）操
...
# 辺（1 行 = 端 / 端 / 型・タブ区切り）
```

### 6.2 大きさ（実測・実際に組んで測った）

| | 行 | byte |
| --- | --- | --- |
| 節点の索引 | 285 | 27,392 |
| 辺の索引 | 494 | 4,959 |
| 合計 | 779 | **32,351（31.6 KiB）** |

設計文書の正本の合計は 550,398 byte なので、**全体像は正本の 5.9%** で得られる。

### 6.3 CLAUDE.md には載せない

規則の表の行 R-2 は CLAUDE.md の生成区間の本文を 8,000 byte 以下に縛る（実測の余地は 88 byte）。**32 KB は載らない。** 載せようとすれば条 P-14.3 と行 R-2 に反する。

代わりに、`folio hello`（いまは「設計文書がまだ無い」の案内 1 行だけ）に **設計文書が在るときの 1 行** を足す。字は「設計文書 285 節点・494 辺。全体像は `folio graph --digest`」。1 行なので非機能要件 NFR1（AI へ常時渡す説明文の合計・母集団は行 R-1）の母集団にも収まる。`folio hello` が repo に何も書かない性質（印は `--state` の下だけ・N-1）は変えない。

### 6.4 ここで作らないもの

図は作らない。節点 285・辺 494 のグラフの図は人が読めるものにならず、図の型の閉じた一覧（規則の表の行 R-5・8 型）にも無い型を要求する。持ち主が「全体像」と言ったのは **AI にとっての** 全体像であって、絵ではない。

## 7. 台帳との絡み

### 7.1 向き

**台帳へは書かない。** 台帳は規則を持たない（P-5.4）。folio が台帳を読むのは **読み取り専用** で、`bd --readonly list --all --json` の出力を受け取るだけにする。台帳が無い環境では、台帳に由来する欄を「まだ分からない」にして残りを出す（P-4.2）。

### 7.2 何を繋ぐか

```
要件（FR20）
  └─ 契約表の行（delivery-72.md#bu の req 欄）        ← 87 行・181 件
       ├─ 台帳の bead（f2-648.107 の design pointer） ← 42 件 → 40 行
       └─ 着地の commit（Scribe2-Contract の印）       ← 34 commit
```

3 つの欄はいま別々の場所にあり、突き合わせは人の頭の中にしかない。索引はこれを 1 つの表にする。

### 7.3 「要再読」

契約が受け付けられた後にその要件の節点が変わったら、**便の側に「要再読」を出す**。判定は決定的にできる。

- 契約の行の `req` が指す要件の節点の要約値を、台帳の bead が open になった時点の印の値と比べる。
- 違えば「要再読」。同じなら黙る。

これは便を止める仕掛けではなく、**席と器への知らせ**である。止める判断は門（FR20）が別に持つ。増設しない（N-5 の向き）。

### 7.4 台帳の依存の辺を取り込むか

取り込まない。bead の依存は作業の順序であって、設計文書の関係ではない。台帳から読むのは design pointer（bead → 契約の行）1 種類だけにする。

### 8.2 憲法の改訂が要らない理由

- P-3.1（機械で決定的に検査できる項目は床に置く）— 影響集合の導出は決定的なので床に置ける。新しい段を作らない。
- P-3.2 / N-5（観点を増やさない）— 観点は 4 つのまま。読む範囲が変わるだけ。
- P-6.3（同じ内容を 2 つの面が持つとき、一方を正本とし他方は導出する）— 索引は導出物（§2.3）。
- P-4.2（判定できないものは「まだ分からない」）— 持ち越しの条件が揃わなければ「まだ分からない」（§3.3）。
- P-5.1 / P-5.6（規則は型付きデータ・実装の定数の写しを導出）— 節点の種類と辺の型の閉じた一覧は実装の定数で、生成区間へ導出する（FR19 の対象に足す）。
- N-3.1（例外機構を足さない）— 持ち越しは旗でも口でもない（§3.3）。

**本構想は ADR-8 の帰結の範囲（天井の形）と要件書の版上げで運べる。** 条文を 1 字も動かさない。動かす必要が出たら、それは §10 の grill で見つかるべき欠陥である。

## 9. 退ける案

### 9.1 根本から作り直す（持ち主の第 2 の選択肢）

**退ける。実証がある。** §1.7 の実測で、**過去 23 周・整合の所見 142 件のうち、型付きの辺で 2 段を超えて離れていたものは 1 件も無かった**。いま在る辺の型（§1.2 の 20 種・641 本）で足りている。

これに加えて、床（規則の表の行 R-4）は未解決の参照 id を 0 に保ち、条と規則行の双方向を強制している。id の規律（P-7.1）も append-only で効いている。**作り直したときに手に入るものが、いま在るものと同じである。** 失うものは 12 本の判断の記録と 27 条と 20 要件の id の連続性（P-7.1 が禁じる改番）と、3 本の凍結 anchor である。

### 9.2 file 単位のまま（いまの形を続ける）

**退ける。** §1.6 の実測で、文書の単位では中央値 2 文書（9 つのうち 22%）が丸ごと古くなる。25 周を 3 日で回した実績（§1.5）が続く。判断の記録 ADR-8 の門の撤退条件（設計文書を触る便が 1 週間に 5 本を超え、周の費用が便の費用の合計を超えたら）は既に満たされている。

### 9.3 散文の言及を辺にする

**退ける。** §2.2 の 4 つの理由（数が 2.7 倍・向きが無い・N-2 に反する・そして §1.7 が「要らない」を実証した）。

### 9.4 文書ごとの印（`ceiling-gate.md` §4 案 B）

**節点の単位に置き換える。** 案 B は「× 整合の観点は差分にできないので費用は半分にしかならない」と自分で書いていた。実測ではそのとおりで、整合 は読む欄だけに絞っても 70.9% を読む（§1.5）。節点の単位にして 2 段の近傍で切ることで初めて 整合 も増分になる。案 B を退けるのではなく、**同じ意図をより細かい単位で果たす**。

### 9.5 近傍を 1 段で切る（本ノートの当初の起草）

**退ける。§1.7 で自分の案を実測が否定した。** 1 段では整合の所見の 16%、重さが「止める」の 12 件のうち 1 件を取りこぼす。この 1 件（2026-09-20 round3 の F-2・規則の表の行 R-8 と制約 CON5 と判断の記録 4 本の食い違い）は、増分で回していたら見落としていた。

費用は 1 段の中央値 35% に対して 2 段は 53% で、18 ポイント高い。**その 18 ポイントは、止める所見 1 件の取りこぼしを防ぐ値段である。** 天井は意味の検査で、床のように取りこぼしを別の口が拾ってくれる層ではない（P-3.2・P-3.3）。

### 9.6 3 段以上の伝播

**退ける。** §1.7 で 3 段以上の所見が 0 件。次数の高い節点（P-5 が 35・ADR-8 が 32）を 2 つ通れば辺を持つ節点 190 の大半に届き、増分でなくなる。代わりに 3 段目の id の列を隠さずに添える（§3.2）。

### 9.7 グラフを人が書く file に持つ

**退ける。** P-6.4（2 つの面を人が書き、一致を検査で強制する設計を採らない）。索引は導出物だけにする。

### 9.8 床を「憲法だけ」にする（持ち主の指示の字面どおり）

**退ける。** §1.7 の実測で、語彙の語に 17 件・天井の観点に 12 件の所見が置かれている。この 2 つは型付きの辺を 1 本も持たないので、伝播では永久に届かない。床を憲法だけにすると、この 29 件の所見が出る経路が閉じる。語彙と規則の表は入口の棚で憲法の付録と定められており、**憲法の一部として毎周読む**（§3.1）。費用は 12.6% → 30.8%。

## 10. 撤退条件と、敵対的検証（grill）で問うべきこと

### 10.1 撤退条件（P-8.1・数えるのは orchestrator 席・記帳は台帳 f2-648）

1. **影響集合が取りこぼす**: 増分で回した周の後に、影響集合の外に在った節点についての「止める」の所見が、次の全部読みの周で出たら数える。**2 件で本判断を捨てる**（増分をやめ、全部読みに戻す）。数えるために、増分の周を **5 周ごとに 1 回** は全部読みの周で挟む（この比は判断の記録の撤退条件の欄に置く）。
2. **持ち越しが誤る**: 持ち越した観点の判定が、後の全部読みの周で覆ったら数える。**1 件で持ち越し（§3.3）だけを捨てる**（影響集合の絞りは残す）。
3. **索引が費用を取り戻さない**: 索引を組む口（G1）の実行時間が 1 周の節約分を超えたら数える。**実測 3 回で G5 の絞りを止める**（索引と全体像の出力は残す）。
4. **2 段でも足りない**: 型付きの辺で 3 段以上離れた節点を結び付ける「止める」の所見が **2 件** 出たら、半径を 3 に上げるのではなく、§9.1（根本から作り直す）の設計ノートを起こす。3 段まで広げると増分でなくなるので、そのときは辺の型が足りていないという意味になる。
5. **門を緩めたことの対価**: 節点の単位の門（§4.3）が「通す」を返した便の後に、その便が触らなかった file の不合格の節点が **2 周以上** 放置されたら数える。**2 回で §4.3 を捨て、門を repo 全体の判定に戻す。**

### 10.2 grill で問うべき 5 つ（A-2.3）

1. **§1.7 の数えは正しいか。** 本ノートの根拠の大半がこの 1 つの実測に乗っている。数え方には 3 つの弱点がある。(a) 所見が結び付けた相手を `note` と `evidence` の中の id の走査で取っており、所見の書き手が id を書かずに言葉で指した関係は数えていない。(b) 距離は「いまの辺」で測っており、当時の辺ではない。(c) 整合 の観点だけを数え、ほかの 3 観点は数えていない。**この 3 つを潰したとき、2 段で 100% は保たれるか。**
2. **散文の言及を捨てて損をしないか。** §1.3 の 1,709 件の中に、型付きの欄に無い「本当の依存」がどれだけ混ざっているか。標本を取って数え、混ざっていたなら、それは辺にするのではなく **型付きの欄へ書き写す便** を先に起こすべきではないか。
3. **持ち越しは N-3.1（例外機構）ではないと言い切れるか。** §3.3 は「同じ入力に同じ判定」と言うが、天井は AI の判定であり、同じ入力でも同じ答えが返る保証は無い。前の周の AI の判定を今の周の判定として扱うことは、**AI の非決定性を隠す旗** ではないか。P-3.3（床の合格を天井の合格として扱わない）と同じ罠に落ちていないか。§1.8 の効きのうち持ち越しの寄与は測っていない（③ の中に混ざっている）。**持ち越しを捨てても ① ② ③ の大半は残るのではないか。残るなら捨てるべきではないか。**
4. **門を緩めることの対価は何か。** §4.3 は判定の対象を repo 全体からこの便の file へ狭める。狭めた結果、「不合格の節点が在るのに、それを触らない便が通り続け、不合格が放置される」経路が開く。判断の記録 ADR-8 決定 (4)（天井が合格でない間は着地を止める）の狙いが、この変更で何割残るか。残す仕掛け（通したときに古い節点の数を必ず出す・撤退条件 5）は十分か。
5. **実装の状態を注から追い出すと、何が読めなくなるか。** §5.3 は要件書の注から実装の状態の文を落とす。落とした後、持ち主が要件書の面を開いたときに「これはもう動くのか」が読めるか。導出物が面に出ていなければ、**人に対しては劣化** である。面の側の便（FR4 の生成器）を §8 の列に入れるべきではないか。

### 10.3 grill の材料として渡すもの

- §1.7 の数えの手順と生の結果（142 件の所見ごとの 場所・指す先・段）。
- §1.8 の 40 commit ごとの割合。
- 本ノートの起草が 1 段から 2 段へ覆った経緯（§9.5）。**起草が自分の案を実測で否定した記録そのものが、検証役への材料である。**
